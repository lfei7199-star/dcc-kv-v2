# 16 统一记录规范与分阶段验收（2026-11-25）

> 范围：把 `accept.py`（2A）与 `two_d.py` / `record.py`（2C / 2D）的记录口径整合成**一个外壳 + 分离诊断子结构**，
> 并让校验器按「stage × scope × 字段组合」而不是「字段是否存在」判。
> 本轮**没有**提交任何 GPU 作业（0 次），**没有**触碰 `src/legacy/`、冻结执行文档、preregistration、registry、unlock、ledger，
> **没有**把任何 CPU 结果写成真实 NCCL 2A 或真实 DCC 2D 通过。

---

## 0 裁定要点

西瓜先生本轮的调整，一句话：**统一的是记录格式，不是证据**。

- 2A 验证的是 Dense SP 的分片、驻留、通信与 Attention 数值正确性；它没有执行 Key Selection、β 拟合、Value OLS，
  因此 `beta_bind_hi`、`mass_residual`、`value_design_cond` 在 2A 上**不存在**。为格式统一而填默认值，等于让审计记录失真。
- `accept.py` 接入记录要走独立 adapter/validator，**2A 验收逻辑不得直接依赖 `compact.py` 的求解器**。
- 三条防护：`NOT_APPLICABLE` 与 `MISSING` 必须分开；记录校验查 stage/scope/字段组合；CPU 记录仍不能获得真实 NCCL/SP 的 PASS。
- 两个特别注意：2A 与 2D 的关联 ≠ 共享一次运行；统一 schema 之后必须补负向测试。

验收目标（原文）：**同一种记录格式能够真实表达 2A 的 SP 正确性，也能够表达 2D 的逐边压缩构造；
但两个阶段各自只对自己实际测量的证据负责。**

## 1 结构：一个外壳，分离诊断

```
experiment_record
├── schema_version          dcckv-experiment-record/1
├── experiment_id
├── stage                   2A / 2C / 2D
├── scope                   evidence_level + claims（受控词表）+ does_not_claim
├── provenance              vcs/commit、files+sha256、config_sha、environment
├── topology                world_size、ranks、source、destinations、rank_map、layout
├── workload                model(synthetic 必填)、seq_len、position_ids、dtype
├── sp_structure            status + rank_topology / owner_kv / remote_staging /
│                           no_full_copy / communication / gqa_repeat / numerical
├── compact_diagnostics     status + entries[]（每条边五块）+ destination_semantics
├── upstream_refs           只引用，不替代（见 §7.1）
└── verdict                 由 checks 重算，含 ceiling / partial / blocked
```

三份记录的外壳键**完全相同**（`tests/test_envelope.py::TestSharedShape::test_shell_keys_are_identical` 断言），
差异只出现在两个子结构的 `status` 上：

| | `sp_structure` | `compact_diagnostics` |
|---|---|---|
| 2A | `APPLICABLE`（真实 dense SP 读数） | `NOT_APPLICABLE` + 理由 |
| 2C | `MISSING` + 理由（这次没有 SP 进程） | `APPLICABLE`，1 条构造 |
| 2D | `MISSING` + 理由 | `APPLICABLE`，逐边 3 条 |

**为什么 2A 的压缩块不是空字典而是带理由的 `NOT_APPLICABLE`：**
空字典无法区分「2A 从来没有这个量」与「记录生成器漏了」。写成带理由的三态，未来任何读者（包括我自己第二轮）
都只能得出一种解释。

**为什么 2D 的 SP 块是 `MISSING` 而不是 `NOT_APPLICABLE`：**
2D 是**跑在 SP 之上**的阶段，它天然要有 SP 记录；这次没跑是**证据缺口**，不是不适用。这两句话在审计上完全不同：
前者要补一次 GPU 运行，后者永远不必补。

## 2 三态语义

| 状态 | 含义 | 2A 的例子 | 2D 的例子 | 判决后果 |
|---|---|---|---|---|
| `APPLICABLE` | 本阶段执行了，数字是自己的 | `owner_kv` | `beta_binding` | 进入数值校验 |
| `NOT_APPLICABLE` | 本阶段**结构上没有**这个量 | `compact_diagnostics` | `destination_semantics`（2C） | 必须为空；带数字即拒收 |
| `MISSING` | 本阶段**应该有**、这次没有 | （非法：2A 的 SP 行） | `sp_structure` | 看需求等级 → 拒收 或 BLOCKED |

- `envelope.classify_block(None) == MISSING`：**缺块一律读作 MISSING**，不会被读成"不适用"。
  这是这套规范里最容易被实现细节破坏的一条，所以它有独立单测。
- 2A 若把压缩块写成 `MISSING`，拒收消息是
  `compact_diagnostics is MISSING but 2A does not execute selection/beta/Value OLS, so compact_diagnostics must be NOT_APPLICABLE`。

## 3 需求矩阵（数据驱动）

矩阵是**数据**，不是散落在代码里的 if：

```python
REQUIREMENT_TABLE = {
  "rank_topology":          {2A: required, 2C: required_evidence, 2D: required_evidence},
  "owner_kv_resident":      {2A: required, 2C: required_evidence, 2D: required_evidence},
  "remote_staging":         {2A: required, 2C: required_evidence, 2D: required_evidence},
  "no_full_copy":           {2A: required, 2C: required_evidence, 2D: required_evidence},
  "communication":          {2A: required_evidence, 2C: required_evidence, 2D: required_evidence},
  "beta_binding":           {2A: forbidden, 2C: required, 2D: required},
  "beta_value_rank_cond":   {2A: forbidden, 2C: required, 2D: required},
  "mass_residual":          {2A: forbidden, 2C: required, 2D: required},
  "destination_semantics":  {2A: forbidden, 2C: forbidden, 2D: required},
}
```

| 等级 | 缺失时 |
|---|---|
| `required` | 记录失效 → 拒收（`FAIL`） |
| `required_evidence` | 记录成立、证据不足 → `BLOCKED_CPU_NO_GPU_EVIDENCE` |
| `forbidden` | 出现数字 → 拒收（这条正是 2A 填 β 的防线） |

与裁定表的对应：裁定给的「必须检查」在 2A 上是 `required`（2A 自己的主题就是 SP，缺了不是缺口而是记录坏了），
在 2C/2D 上是 `required_evidence`（阶段主题是构造，SP 是它运行的环境）。
「不适用」一律 `forbidden`。**矩阵本身有测试断言**（`TestRequirementTable`），改矩阵会同时改行为，
不会出现"矩阵写一套、校验跑另一套"。

**`communication` 一行是例外，三个阶段都是 `required_evidence`。**
它记的不是「有没有跑」，而是「跑出来的数从哪来」：`evidence` 必须写 `declared_structural` 或 `measured_nccl`，
后者还额外要求 `scope.evidence_level = measured_hardware`。所以这一行永远有内容、永远被检查，
而在 CPU 上永远是 `BLOCKED`——这是裁定第三条防护（CPU 记录仍不能获得真实 NCCL 的 PASS）在矩阵里的落点。

**两层 schema 不是重复。**
`record.py` 的 `dcckv-edge-record/1` 是**内层**：逐边构造明细，含 beta/values 张量、原始残差与分母。
`envelope.py` 的 `dcckv-experiment-record/1` 是**外层**：跨阶段可比的标准投影。
外层 entry 只带 `inner_schema` + `payload_digest` 指回内层，**不复制张量**——
所以两者不会各自漂移，而 2C 的 328 KB 级文件也不会因为统一而翻倍。

**2A 不依赖求解器，是机器可查的。**
`TestImportIsolation` 在**子进程**里 `import src.v2.cpu_ref.adapter_2a`，断言 `compact` 与 `record`
根本没被加载；同时断言 `adapter_compact` **会**加载 `compact`——否则上面那条可能只是 Python 的偶然。

**`accept.attach_envelope` 的三条拒绝**
1. stage 不是 2A（2D 记录不能冒充 2A）；
2. 记录自称 `PASS`（CPU 上不可能，出现即人工编辑）；
3. 记录判决与它要描述的 checks 不一致。

## 6 三条防护

### 6.1 `NOT_APPLICABLE` ≠ `MISSING`
见 §2。独立测试：`test_2a_declaring_compact_missing_is_rejected`（2A 写 MISSING 被拒）、
`test_2d_declaring_compact_missing_is_rejected`（2D 写 MISSING 被拒，消息是 `incomplete evidence`）、
`test_2d_sp_missing_is_a_gap_not_a_defect`（2D 的 SP MISSING 记录成立、判决 BLOCKED）。

### 6.2 查 stage / scope / 字段组合，不只查存在性

| 规则 | 违规示例 | 消息 |
|---|---|---|
| stage 决定 topology 形态 | 2A 带 `destinations` | `2A has no destination set; destinations [0, 1, 2] were recorded` |
| stage 决定 claim 词表 | 2A 声明 `shared_query_construction` | `claim 'shared_query_construction' is not in the 2A vocabulary [...]` |
| 证据等级决定 claim 上限 | 声明 `nccl_transport` 但 level 是 `structural_cpu` | `claim 'nccl_transport' needs measured hardware evidence, level is 'structural_cpu'` |
| `communication.evidence = measured_nccl` 需要 level 也是 measured | 只改 evidence 字段 | `communication claims a measured NCCL record while the evidence level is not measured_hardware` |
| 声明了 SP 就必须填满 SP 五行 | 删掉 `owner_kv` | `sp_structure.owner_kv is MISSING while the SP block claims a run (...)` |
| 压缩块 `APPLICABLE` 就必须同时有 `compact` 检查行 | 只改状态不加行 | `compact_diagnostics is APPLICABLE but no compact check row exists` |
| 未跑 SP 就必须有 BLOCKED 行 | 删掉所有 BLOCKED 行 | `sp_structure is MISSING but no SP row is BLOCKED; a stage that did not run SP cannot fold to a pass` |

`scope.does_not_claim` 是**必填**且不能与 `claims` 相交——一条记录必须说出它不声称什么。

### 6.3 CPU 记录仍不能获得真实硬件 PASS

判决不是声明出来的，是**重算出来的**：`validate` 调 `fold_verdict(checks, evidence_level)`，
与记录里写的 `overall` / `ceiling` / `blocked_requires_gpu` 逐项比对。
`evidence_level = structural_cpu` 时天花板是 `PASS_CPU_SEMANTICS`，`PASS` **不可达**。
2A 侧还有第二道：`accept.attach_envelope` 看到 `PASS` 直接抛异常。

结果是三份记录的判决都是 `BLOCKED_CPU_NO_GPU_EVIDENCE`（§8），
`partial.compact` 在 2D 上是 `PASS_CPU_SEMANTICS`——**构造语义通过，阶段整体阻塞**。

## 7 两个特别注意的问题

### 7.1 2A 与 2D 的关联 ≠ 共享一次运行

- 2D 记录通过 `upstream_refs` 引用 2A 的 `experiment_id` + 判决 + 文件 sha256，**只引用，不搬运**。
  测试 `test_citing_2a_does_not_change_the_verdict`：加了引用之后，2D 的判决逐字不变。
- 结构性防线：SP 子块内出现 `from_upstream` / `upstream_value` / `borrowed_from` 一律拒收
  （`an upstream reference cannot supply this stage's own measurement`）；
  `sp_structure` 未跑却带着 `owner_kv` 数字，拒收（`must not be padded with numbers`）。
- 本节的实际后果：**不能拿 2A 的通信字节数或驻留量代替 2D 自己的测量**。这次 2D 没有 SP 测量，
  所以它的 SP 块是 `MISSING`，五条 SP 行全 `BLOCKED`，判决不进 `PASS`。

### 7.2 统一 schema 之后补的负向测试

除 §5 五条，还补了这些（都在 `tests/test_envelope.py`，共 88 条）：

| 类别 | 断言 |
|---|---|
| 判决重算 | 手改 `overall` / `ceiling` / 删 BLOCKED 行，三种都被拒 |
| 字段组合 | 2A 带 destinations；2A 把压缩块改成 `APPLICABLE`；`beta_design` 与 `value_design` 共用 `problem`；β 盒上下界反转 |
| 溯源 | `vcs=git` 但 commit 不是 40-hex；无仓库却写了 commit；`files` 为空 |
| 工作负载 | 真模型缺 revision（`HF 'main' is not a revision`）；`rope_phase_verified` 未声明 |
| 2D 拓扑 | entry 数 ≠ 目的端数；目的端不在 topology；两个 entry 同一目的端；无 source |
| 目的端语义 | `shared_query_set=True` 但哈希不同；`per_destination_queries` 不是显式布尔 |
| 数值块 | 缺 `method`（rank 没有产生它的方法不可比）；`bind_hi_frac` 越界；`mass_residual.normalized` 为负 |
| 隔离 | 子进程断言 `adapter_2a` / `accept` 不加载 `compact`、`record`，而 `adapter_compact` 会加载 |

## 9 状态边界的维持（明确不宣称）

- **2A 仍是 BLOCKED。** 没有 NCCL、没有 `all_to_all_v`、没有 CUDA backend；`2A-05` 恒 `NOT_APPLICABLE_NO_CUDA`。
- **2D 的阶段判决是 BLOCKED。** 构造语义 `PASS_CPU_SEMANTICS` 只覆盖 2D-01…06 与 2D-07，
  不覆盖"分布传输"这一侧。
- **2D-06b 仍 BLOCKED。** 元数据能往返 ≠ RoPE 相位正确。这一条这次**没有**被记录规范化掩盖：
  它现在是 `workload.position_ids.rope_phase_verified=false` 加上 2D-06b 的 BLOCKED 两处共同记录。
- **`dead_frac = 0` 仍是 null 结果**（五档预算、合成 iid 高斯键）。它证明的是计数逻辑在测试条件下可运行，
  **不证明**真实 KV 上"质量补偿诊断"已有分辨力。本轮没有把它写进任何"有效"叙述。
- **没有新结论，只有新记录。** 本轮不改任何数值性主张。
