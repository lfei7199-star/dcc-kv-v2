## 1. 四档取值

| 每条边保留预算 | 三条边合计 | 每边压缩倍数 `T/t` | 占 98208 比例 | 相对 1637 |
|---|---|---|---|---|
| **819** | 2 457 | 39.97× | 2.50% | 0.5× |
| **1637** | 4 911 | 20.00× | 5.00% | **1×（主预算，已冻结）** |
| **3274** | 9 822 | 10.00× | 10.00% | 2× |
| **6548** | 19 644 | 5.00× | 20.00% | 4× |

三个口径必须分开写，混用会算出 3 倍误差：

- **每边压缩倍数** = `32736 / t`。32736 是每个 rank 经 SP 分片后的序列长度（130944 / 4）。
- **三条边合计** = `3 × t`。1637 时为 **4911**，不是 4910（`4910 = 3×1636.67` 是四舍五入的产物）。
- **占 98208 比例** = `3t / 98208`。98208 = `3 × 32736`，是**一个接收端**看到的三个远端源块的原始 token 总量。

⇒ 819 是 `ceil(1637/2)`，四档即 **0.5× / 1× / 2× / 4×** 的倍率序列。这一点要在图表脚注里写明，否则读者会以为 819 是独立选的。

## 2. 为什么要第四档（20%），而不是三档

合成探测的趋势是「C 的优势随预算放宽而衰减」（预算 4→24 时，C 优于 B′ 的格子数 9/9 → 5/9）。若只取 819/1637/3274 三个较紧的点，可能整段都落在"优势成立"区间，看不到**衰减与反转**。

加入 6548（5×）这一档，回答的是：**Destination-specific Query 的价值是否只存在于激进压缩区间？预算放宽后 B′ 与 C 是否趋同？** 这是 §2 假设 H3c（迁移矩阵对角线）在预算轴上的对应检验，缺了它，H3c 只能在一个方向上被支持。

## 3. 公平性约束（四档必须逐条满足）

| 约束 | 说明 |
|---|---|
| 同输入 | 同一批 21 条请求、同一 input_ids、同一 L=130944 |
| 同预算 | 同一档内 B′ 与 C 的 `t` 逐边相等 |
| 同 Key 选择器 | 同一 `selector`；**不得 B′ 用一种、C 用另一种** |
| 同 β / Value 算法 | 同一 `beta_mode`、同一 `lambda`；参数只在两边完全一致时才有归因力 |
| 同参考 Query 数量 | 同档同边，`n_ref` 相同 |
| 同评测样本与指标 | 同一 200 条子集、同一 rel-L2/KL/top-k 口径 |

> 这一条在 AM 升级后会变得更敏感：若 B′ 与 C 用了不同的 `beta_mode`（例如 B′ 用标量、C 用逐 key），那么测到的差异**无法归因给 Query 条件化**，只能归因给 β 形式。见 `design/12` §6.1 的 U-5。

## 4. 反例的预登记处理

已知现象：合成探测中 seed 41 的 destination 0 在多个预算段出现反转（C 不优于 B′）。

**处理方式（现在就写死，避免事后裁剪）**：

1. 四档全部报告，包含所有 seed / destination 格，**不做剔除**。
2. 反转格**必须单独列出**，不得只报均值——这是 §9 风险 R6「均值掩盖单个 Destination 退化」的具体落点。
3. 允许的表述：「在 X 档、Y 个目的端格中，C 与 B′ 的差值为负」。**不允许**的表述：「C 全面优于 B′」。
4. 反转本身是结果，不是异常。若某档出现系统性反转，那说明 Query 条件化在该压缩率下有害——这比"全面更优"更有信息量。

## 5. 与 AM β 盒约束的耦合（本次新增，必须预登记）

这一条来自 `design/12` §3.3 的实测，是本文件与旧执行文档唯一的实质增量。

AM 的 HighestAttnKeys 分支把 β 限制在 [−3, 3]（C.2）。`w_j` 的物理含义是"该保留 key 承担多少个原始 key 的质量"，量级约 `T/t`：

| 预算 | `T/t` | `log(T/t)` | 盒顶 e³ | 顶格比例【实测-合成，3 seed 区间】 | 盒内 mass_res |
|---|---|---|---|---|---|
| 819 | 40× | 3.69 | 3.00 | **0.60 – 0.90** | 0.43 – 0.55 |
| 1637 | 20× | 3.00 | 3.00 | **0.15 – 0.40** | 0.27 – 0.29 |
| 3274 | 10× | 2.30 | 3.00 | 0.00 | 0.26 – 0.36 |
| 6548 | 5× | 1.61 | 3.00 | 0.00（β_max 2.999，逼近未顶格） | 0.22 – 0.42 |

⇒ **819 那一档的读数，同时包含"压缩更狠"与"质量补偿被天花板截断"两个因素，不能单独归因为压缩率。** 40× 时 `log(T/t)=3.69` 已经超过盒顶 0.69 nats；20× 时 `log(T/t)=3.00` 恰好落在盒顶，所以主预算本身就已经在边界上。

**因此每档必须同时记录以下字段**（缺一则该档只能作趋势参考）。定义以 `src/v2/cpu_ref/record.py` 的 `DEFINITIONS` 为唯一来源，本表只是摘要；**两处的容差与分母必须一致，否则记录不可比**：

| 字段 | 定义（2026-11-25 定稿口径） | 用途 |
|---|---|---|
| `beta_bind_hi` | `\|β_j − 3\| ≤ 1e−6` 的 key 数量与占比。容差 **固定 1e−6 β 单位**，不由每次运行自定 | 判断该档是否被截断污染 |
| `beta_bind_lo` | `\|β_j + 3\| ≤ 1e−6` 的 key 数量与占比 | 下界饱和；**这与 `beta_dead` 是两个量** |
| `beta_dead` | 贡献 `c_j = w_j·Σ_i A_ij` 小于 `1e−6 × Σ_j c_j` 的 key 数量与占比。分母是**保留 key 上的贡献之和**，`A` 是**全部 calibration Query 堆叠**后的 β 设计矩阵 | 判"该 key 是否仍在承担质量"。盒内 `w_j ≥ e⁻³ > 0`，所以它**不是** `w_j=0`，也不能当 `beta_bind_lo` 用 |
| `mass_residual` | `‖Aw − m‖₂ / ‖m‖₂`，其中 `A, m` 按**全部 calibration Query 堆叠**后一次取范数（pooled），**不是**逐 Query 比值再平均。同时保存原始残差 `‖Aw−m‖₂` 与分母 `‖m‖₂` | 质量匹配本身是否成立；只存比值无法区分"大质量拟合得好"与"小质量凑巧对" |
| `beta_design_rank` / `beta_design_cond` | β 拟合矩阵 `A`（`n_ref × t`）的数值秩与条件数 | 判断 β 解是否可信 |
| `value_design_rank` / `value_design_cond` | Value OLS 设计矩阵 `X`（`n_ref × t`，行是保留集上的 softmax）的数值秩与条件数 | 判断 Value 解是否可信 |

⚠️ **`beta_design` 与 `value_design` 是两个不同的最小二乘问题，不得共用一个 rank 或 cond。** 合成实测中两者条件数可差三个数量级（见 `design/15` §6），合并成一个数字会同时描述不了这两个问题。

## 6. 参考 Query 数量随预算放大（资源后果）

逐 key β 拟合 t 个参数。OLS/盒约束都要求 `n_ref ≥ t`，合成诊断显示 `n_ref < 2t` 时 per-key 会明显过拟合（§`design/12` §6.2）。

| 预算 | `n_ref` 算术下限 | 合成建议（2t） |
|---|---|---|
| 819 | 819/边 | 1 638/边 |
| 1637 | 1 637/边 | 3 274/边 |
| 3274 | 3 274/边 | 6 548/边 |
| 6548 | 6 548/边 | 13 096/边 |

⇒ 6548 档的参考 Query 需求是 1637 档的 **4 倍**，构造开销也随 `O(L·t·M)` 线性上升。**四档不是四个免费的横坐标点。**

这一条直接把 §10 的 Q16（每目的端 reference query 数）从"待确认"变成"有下界的待确认"。

### 6.1 四档 sweep 必须共用 `n_ref = 13096`（2026-11-25 补定）

上表若直接用于 sweep，会让**预算与拟合样本数同时变化**：819 档用 1638 个 Query、6548 档用 13096 个。那么"质量随预算怎么变"里混进了"拟合样本变多"的效应，无法归因。

因此正式四档 sweep（仍待资源授权）规定：

| 项 | 规定 |
|---|---|
| 每边 `n_ref` | **13096 = 2 × 6548**，四档一律相同 |
| B′ | 三条边复用同一套 13096 条共享 Query（按条边池平衡抽取 4366/4365/4365） |
| C | 每条边使用对应 Destination 自己的 13096 条 Query |
| held-out | 与 calibration 严格隔离，四档用同一 held-out 集 |
| 唯一变化因素 | 每边保留预算 819 / 1637 / 3274 / 6548 |

代价是 819 档的 `n_ref/t = 16`，远超 2t，构造开销按 13096 而非 1638 计——**这是为归因干净付的钱**。

⚠️ 单档独立运行（不参与 sweep）仍可用 `n_ref = 2t`，主预算即 3274。两种配置的记录**不可混在同一张图里**：`n_ref` 不同就是不同的拟合问题。

**实测支撑**：`tests/test_2d_conditioning.py` 里两条对照 —— `n_ref = 2t` 时提高预算会换掉 Query 样本，保留集**不嵌套**；把 `n_ref` 固定后保留集严格嵌套（`⊂`）。这从代码层面证实了耦合存在，不是纸面担心。
