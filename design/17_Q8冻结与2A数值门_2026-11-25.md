## 2. 落到哪里：一个零依赖模块

`src/v2/cpu_ref/q8.py`（9 768 B）。**只 import `math`。**

这不是风格问题。`accept` 和 `envelope` 都依赖它，它不依赖任何东西，所以：

- 2A 验收器不会因为求解器 bug 而失败（这条 `test_envelope.TestImportIsolation` 早就在守）；

## 3. 门是三行，不是一行

裁定的 Gate 是一个合取式。实现上拆成三行，因为它们的失败含义完全不同：

| 行 | 检查 | 失败时 | 为什么必须分开 |
|---|---|---|---|
| 2A-04 | `rel_l2 ≤ 1e-5`，含 NaN/Inf 与 shape 前置检查 | FAIL | 唯一的主数值判据 |
| 2A-04b | 预登记位置全部采样、全部有限、reference 在每点都在 | FAIL / BLOCKED | 全局值通过不能替代"某个边界没有输出" |
| 2A-04c | reference 身份与 SHA256 一致 | BLOCKED（INVALID） | reference 找不到 ≠ 误差大；这是比较无效 |

分开的直接收益：**不会出现「RelL2 很小但张量里有 NaN，因此仍然 PASS」**。`check_numeric` 先扫非有限值，命中就返回，`rel_l2` 字段保持 `None`——数值上根本没有被算出来，记录里也就不会出现一个好看的数。

同样的理由加了 shape 前置检查。原来的 `rel_l2` 用 `zip` 逐行比较，**少一个 rank 时会静默截断**，在剩下的行上算出一个漂亮的相对误差。现在形状不等直接 FAIL，`reason = "shape_mismatch"`。

## 4. 为什么 1e-9 不能当门（复述裁定理由 + 本轮的数值）

浮点加法不满足结合律。2A 恰好制造了这条链：

```
不同 rank 分块 → 不同 reduction 顺序 → Online Softmax / LSE 归并
```

CPU 与 GPU、不同 kernel、BF16 配 FP32 upcast，即使输入相同也不保证 bitwise identical。用 1e-9 卡真实 4-GPU 运行，会把正常的归并舍入判成实现错误。

本轮 CPU 实测给了一个可对照的读数：同一批张量走 dense 与 4-rank SP，`rel_l2 = 2.41e-16`。这是 float64、同一进程、同一求和实现的误差——**它证明的是算术路径一致，不能证明 1e-9 对 BF16 合理，更不能证明 1e-5 对 BF16 合理**。后者只能由真实运行给出，见 §8。

---

## 5. 为什么 1e-5 是一个站得住的工程阈值

它是预先冻结的工程值，不是从模型长度、卡型或某个"通用标准"推导的。选它的两个条件：

- 不把正常浮点归并误差当错误（BF16 累加 + LSE 归并的典型相对偏差在 1e-7 量级，1e-5 留两个数量级余量）；
- 不能松到把明显错误放进门。

第二点的量化：真实的 attention/SP 缺陷——少一个块、分片错位、LSE 归并公式写错、mask 漏掉——产生的是**序 1e-2** 的相对误差。1e-5 与它差三个数量级。所以这个门在"正常舍入"与"真错"之间留下了一条很宽的无人区，这正是好阈值的形态。

### 5.1 一个副产品：全局门对小范围局部异常有多敏感

若只有一行 `r` 偏离，偏差 `‖δ_r‖ = ρ·‖o_r‖`，则

```
RelL2_global = ρ·‖o_r‖ / ‖O‖ ≈ ρ / √L
```

在 L = 130944：

```
单个位置可被全局门漏掉的相对误差上限 ≈ 1e-5 · √130944 ≈ 3.6e-3
```

也就是说：**一个边界位置只要有 0.36% 以上的相对误差，全局门就会报警。**这远小于"真错"的 1e-2 量级，所以「按裁定只报告、不设局部门」在主工作负载上不构成实际漏洞。

但这条保护随长度变弱：L = 96 时下限是 9.8e-5。所以 CPU 小张量上的通过**不能**用来论证边界敏感性；它只验证检查器逻辑。这个数字我算出来写在这里，是为了避免以后有人用"全局通过"去替代局部覆盖。

## 6. 预登记位置：规则化，并且和冻结常量对过

执行文档的十个位置是：

```
(32735, 32736, 32737, 65471, 65472, 65473, 98207, 98208, 98209, 130943)
```

`q8` 不把它写成字面量，而是写成规则：每个内部边界 ±1，加末位。

```python
q8.boundary_positions(130944, 4)   # -> 上面十个数字，逐个相等
```

这样同一套逻辑能在 CPU 小张量上跑（L=96, ws=4 → `(23,24,25,47,48,49,71,72,73,95)`），而不是一个无法被测试覆盖的常量。

抄写错误由一条专门的测试守：`TestBoundaryPositions.test_matches_the_execution_document` **回读 `src/legacy/stage2/constants.py` 的 `SAMPLE_POSITIONS`**（只读，不改），断言与规则输出逐项相等。常量复制错了会红。

记录层还有一道：信封校验会用 `workload.seq_len` 与 `topology.world_size` **重算**应有位置，与记录里的 `required` 比对。**记录不能缩小自己的覆盖要求。**

| 位置 | 原状 | 后果 | 改法 |

## 10. 本文件没有做的事

1. **没有用 CPU 数据论证 1e-5 是对的。** CPU 跑出 2.41e-16，只说明 float64 参考实现的算术路径一致；BF16 + 真实 NCCL 的误差分布本轮没有任何数据。1e-5 是裁定，本轮交付的是"这个裁定不可被绕过"。
2. **没有为局部位置另设阈值。** 裁定只冻结了一个全局阈值；在看到十个位置的数值之后再补一个局部阈值，正是 `post_hoc_adjustment = forbidden` 禁止的动作。局部值全部记录并按名列出（`above_threshold`），但状态不由它决定。§5.1 给出了这样做的量化代价。
3. **没有验证 reference 的可复现性。** 只验证了"身份可核对"（SHA 存在且与 manifest 一致）；`reference_10pos.json` 本身能否重算出来，需要 Job 1 重跑，本轮 0 次 GPU 提交。
4. **没有把冻结写进正式 prereg 文件。** 该文件不在本仓库，且属裁定禁止改动范围。本文件 + `q8.py` 是当前唯一权威副本；**提交 GPU 前需要把 §1 的五项抄进 prereg 登记表**，否则机器可读的冻结只在代码里。
5. **`evidence_level` 仍是声明，不是证明。** 记录会拒绝"合成 workload + measured"，也会拒绝"CUDA backend + structural"，但它无法阻止一个人同时伪造 backend 字符串和证据级。这一层靠 job manifest 与提交记录核对，不是校验器能解决的。
