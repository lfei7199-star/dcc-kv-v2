## 2. 2C 记录模板：从"字段"到"口径"

### 2.1 记录的粒度

**每条 Source→Destination 边一条记录**，不是每个实验一条。`edge_record()` 不提供任何"总计"字段，`payload.counted_for` 恒为 `"this edge only"`。

这个选择在 B′/C 上立刻显形：

| 臂 | 构造次数 | 记录数 |
|---|---|---|
| B′（共享 Query） | 1 次构造服务 3 个目的端 | **1** |
| C（逐目的端 Query） | 3 次独立构造 | **3** |

合成量测实测：B′ = 15 条（3 seed × 5 预算），C = 45 条。**构造次数的不对称本身就是被归因的对象**，用汇总记录会把它抹掉。

### 2.2 八个字段组

| 组 | 字段 | 说明 |
|---|---|---|
| 身份 | `edge.source` / `edge.destination` / `budget_tokens` / `n_ref` / `selector` / `beta_mode` / `value_mode` | 归因四要素必须先固定 |
| Query 溯源 | `query_hash_calibration` / `query_hash_heldout` / `n_heldout` | sha256，浮点用 `.17g` 保证可往返 |
| 选点 | `selected_indices` | t 个，去重校验 |
| β 边界 | `beta_bind_hi/lo` 的 count 与 frac、`bind_tol`、`beta_min/max/mean` | 容差 **1e−6 β 单位，冻结** |
| β 死 key | `dead_count/frac`、`dead_rel`、`denominator`、`scope` | 与下界饱和**分开** |
| 质量残差 | `normalized` / `raw` / `denominator` / `aggregation` | pooled 口径 |
| 两套设计 | `beta_design.{rank,cond,sigma_min,sigma_max,tol,method}` / `value_design.{同}` | **不共用** |
| 载荷与求解 | `payload.*` / `payload_digest` / `solver.{method,status,fallback_used,policy}` | 按边计字节 |

### 2.3 四条口径的确定

| 口径 | 定法 | 为什么这样定 |
|---|---|---|
| 触界容差 | `\|β_j − bound\| ≤ 1e−6`，模块常量，**无参数入口** | 若可由运行传入，看完结果再挑容差就永远"通过" |
| `beta_dead` 的贡献与分母 | `c_j = w_j·Σ_i A_ij`；分母 `Σ_j c_j`（仅保留 key） | 盒内 `w_j ≥ e⁻³ > 0`，不存在 `w_j=0`，所以"死"只能是"贡献占比过小" |
| `mass_residual` 汇总 | 全部 calibration Query **堆叠后一次取范数** | 逐 Query 比值再平均会被低质量 Query 的小分母放大，与拟合目标（未加权 LS）不一致 |
| 原始残差 | 与比值**同时保存** | 只存比值无法区分"大质量拟合好"与"小质量凑巧对" |

`DEFINITIONS` 随每条记录落盘；`validate()` 会拒绝 `bind_tol` 或 `dead_rel` 与当前冻结常量不一致的记录。测试 `test_tampered_tolerance_is_rejected` 直接验证这条闸门有效。

### 2.4 顺带补掉的一个实现缺口

写 2D-06 的测试时发现：`build()` **根本不接收 `logical_len`**，一律写成 `len(k)`。也就是说，一个分片的压缩对象会带上自己的长度而不是源的逻辑长度，AM §2 要的那条信息在构造这一步就丢了。

已修：`build(..., logical_len=None)`，`build_edge` 从 source 传入。测试 `test_source_position_range_is_carried_into_the_compact_object` 现在断言 `logical_len=1000 / span=[200,240]` 能同时成立。

**这是测试抓出来的，不是设计时想到的。** 也说明"字段带了"和"值传下去了"是两件事。

## 3. CUDA OLS：求解与诊断分离

你指出的限制成立，且已经落到代码契约里，而不是写在注释里：

```
solve  : torch.linalg.lstsq, driver='gels'   （CUDA 只有这一条）
diagnose: 独立一遍，算 rank / cond / sigma_min
failure: 记录失败，永不切换 ridge / pinv
```

`record.solver_policy()` 返回：

| 字段 | 值 |
|---|---|
| `fallback` | `""`（空串，不是 `"ridge"`，也不是 `"pinv"`） |
| `on_failure` | `"raise_and_record"` |
| `solve_separate_from_diagnose` | `True` |

记录里 `solver.method` 与 `diagnostics.*_design.method` 是**两个字段**：前者说答案怎么来的，后者说 rank/cond 怎么来的。CPU 上都填 `householder_qr_f64_cpu`；将来 GPU 记录必须填不同的值，而 `validate()` 会因 `method` 不同而让两者不可混比。

**已测**：重复 key 造出的秩亏设计矩阵必须抛 `RankDeficientError`，且异常携带 `stats`（`rank`、`rank_deficient`、`r_min`、`r_max`），调用方拿不到任何"已正则化的解"。两条测试分别验证"必须抛"和"policy 里没有回退路径"。

### 4.2 每项证明什么、不证明什么

| ID | 证明 | **不**证明 |
|---|---|---|
| 2D-01 | 三条边用同一套 Query 时，代码路径没有引入目的端相关的偏差 | 不等于 C 退化后就没意义——它只说明"条件化的开关确实是 Query" |
| 2D-02 | 条件化确实接进了构造链（不是把同一个对象复制三份） | **不说明 C 比 B′ 好**。这一点仍只由量测脚本记录，不进验收 |
| 2D-03 | held-out 没有混进选点 / β / Value 拟合 | 不说明 held-out 集本身有代表性 |
| 2D-04 | 每条边按自己的预算构造，不共用、不平均 | 不说明三条边预算之和有任何物理含义 |

### 4.3 一条按你要求"不写"的测试

**没有**任何形如 `assert dcc_error < shared_error` 的门槛测试。测的是身份（digest 相同/不同），不是质量。`check_independence` 只要求"不能三条边全同"，因为要求"两两必不同"是在断言数据、不是在断言代码。

## 6. 实测读数（合成，advisory，不进 Table 4）

### 6.1 两套设计矩阵的条件数差三个数量级

| budget | n_ref | `beta_design_cond` | `value_design_cond` | 比值 |
|---|---|---|---|---|
| 4 | 8 | 48.1 | 55.0 | 1.1× |
| 6 | 12 | 813.3 | 4 676.7 | 5.8× |
| 8 | 16 | 2 640.2 | 156 981.0 | 59× |
| 12 | 24 | 50 990.5 | 153 431.4 | 3.0× |
| 24 | 48 | 1 938 621.4 | 79 442 301.4 | 41× |

⇒ **共用一个 rank/cond 会把 41 倍甚至 59 倍的差异抹平**，这正是你要求分开记录的理由，现在有数了。

⚠️ 但这两个绝对值**不能外推到真实模型**：这组合成 Query 被限制在 2 维子空间里，设计矩阵天然接近奇异。它们的用途是证明"两套必须分开"，不是预测 Qwen 上的条件数。

### 6.2 `beta_dead` 在合成数据上恒为 0 —— 一个必须保留的 null

五个预算点的 `dead_frac` 全为 **0.00**。原因清楚：盒内 `w_j ≥ e⁻³`，而 iid 高斯键的列和量级相当，没有哪个 key 的贡献会掉到总量的 1e−6 以下。

⇒ **这个指标已实现、已单测（用合成贡献向量精确验证计数与边界），但在当前数据上没有分辨力。** 不能说"有效质量占比诊断已可用"，只能说"计数逻辑已验，真实 KV 上待验"。要让它显形，需要真实 KV 里存在"几乎不被任何 calibration Query 关注的 key"。

### 6.3 顶格率随预算收紧单调上升

| budget | 4 | 6 | 8 | 12 | 24 |
|---|---|---|---|---|---|
| `beta_bind_hi_frac` | 0.64 | 0.30 | 0.11 | 0.03 | 0.00 |

方向符合预期：预算越紧，需要补偿的质量越多，越容易撞到 e³ 天花板。这与 `design/12`/`design/13` 里"主预算 20× 恰好踩在 `log(T/t)=3`"的判断一致。

### 6.4 C 与 B′ 的差距（仅记录，不作主张）

45 格中 42 格 C 更优，预算 ≥ 8 时 9/9。**但 budget 与 n_ref 同步变大是混杂**，所以这组数字只能读作"在各自拟合配置下的表现"，不能读作"预算扩大带来了什么"。旧链上那条"C 优势随预算放宽而消失"在新链下不再出现。

### 6.5 CPU 路径的真实规模（纠正我此前的一个说法）

| t | 16 | 32 | 64 | 96 | 128 | 192 | 256 |
|---|---|---|---|---|---|---|---|
| 秒 | 0.06 | 0.14 | 0.37 | 0.79 | 1.44 | 4.00 | 8.75 |
| 局部指数 | — | 1.24 | 1.42 | 1.86 | 2.10 | 2.52 | 2.72 |

指数在向 3 逼近（`O(n_ref·t²)`，`n_ref=2t` ⇒ 三次）。外推 **t=1637：约 23 min/edge（用实测最大指数），约 38 min/edge（按三次）**；三条边 1–2 小时。

⇒ **我此前说"CPU 跑不动 1637"说过头了。** 准确说法是：慢（单拓扑单 seed 单预算 1–2 小时），四档 × 3 seed × 3 边需要几十小时，工程上不划算。**但真正挡住 1637 的不是 CPU 速度，而是没有真实 KV 张量**——即使算得动，输入也是合成的。这两件事我在上一轮混成了一件。
